# transmon_bench_cpu/

geode-vs-Palace CPU timing on the committed transmon mesh. These files are
performance records, not CI gates. The index of the result files is in
[`../README.md`](../README.md). This page holds the tuned-Palace comparison
(#927).

## Tuned Palace on m6i.4xlarge (#927)

[`results_tuned_palace_m6i.toml`](results_tuned_palace_m6i.toml) is generated by
[`summarize_tuned_palace_m6i.py`](summarize_tuned_palace_m6i.py) from
[`runs/2026-10-09_m6i_tuned_palace/`](runs/2026-10-09_m6i_tuned_palace/README.md)
and the PR #964 tree
[`runs/2026-10-08_m6i_like_for_like/`](runs/2026-10-08_m6i_like_for_like/README.md).
To regenerate it, run from the repository root:

```sh
python3 -I benchmarks/transmon_bench_cpu/summarize_tuned_palace_m6i.py \
  benchmarks/transmon_bench_cpu/runs/2026-10-09_m6i_tuned_palace \
  reference/fixtures/transmon_palace/results_p1/eig.csv \
  benchmarks/transmon_bench_cpu/runs/2026-10-08_m6i_like_for_like \
  > benchmarks/transmon_bench_cpu/results_tuned_palace_m6i.toml
```

**Setup.** One AWS m6i.4xlarge (us-east-1, Xeon Platinum 8375C, 8 cores / 16
vCPU), one session, no other workload. Fixture: the committed 133,108-DOF
transmon mesh, first order. Palace `fba6a5b` ran in three builds:

- **Tuned.** Built on the box from
  [`reference/palace/docker/Dockerfile.tuned`](../../reference/palace/docker/Dockerfile.tuned).
  - libxsmm on. The logs show libCEED backend `/cpu/self/xsmm/blocked`.
  - `-march=icelake-server -mtune=icelake-server`, passed to Palace and every
    dependency it builds. AVX-512 instructions are present in every library.
  - OpenBLAS 0.3.29 built for the host (`TARGET=SKYLAKEX`, threading off). It is
    the only BLAS in the image.
  - Release build.
- **Untuned, same box.** The unchanged
  [`reference/palace/docker/Dockerfile`](../../reference/palace/docker/Dockerfile),
  built and timed on the same instance after the tuned sweep. It has no libxsmm
  (`/cpu/self/opt/blocked`) and no `-march`, and its libraries contain no AVX
  instructions at all. It uses Rocky's serial OpenBLAS.
- **PR #964.** The same untuned recipe, timed on a different m6i.4xlarge
  instance earlier the same day.

geode `8367ee7b` (`main` at the start) ran on the same box, interleaved with the
tuned sweep. geode has no host tuning (default x86-64 target CPU), as in PR
#964. Every Palace config sets `Solver.Linear.Type = "SuperLU"` explicitly. The
fixture says `"Default"`, which resolves to SuperLU at this Palace commit. One
control run with `"Default"` gave the identical eigenvalues and GMRES iteration
counts. The pinning is that of PR #964: one CPU per physical core, `taskset`
for geode, and `--cpuset-cpus` plus `-bind-to core` for Palace.

Repeats: 3 runs per Palace cell and 2 per geode cell (the PR #964 Palace
`Save = 0` 1-rank cell is n = 1). The tables give wall seconds as median
(min–max). Core-s is user + sys, median.

**On one box, the tuned build is 1.2% to 4.5% faster than the untuned one.**
The two untuned builds differ by more than that: the same recipe was 3.8% to
6.0% slower on the PR #964 instance. The geode cells differ by 6.3% to 8.9%
between the two sessions as well (`[geode_session_check]`; the geode commits
differ too). So most of the gap between the PR #964 Palace numbers and the tuned
ones is the instance, not the build. A PR #964 / tuned ratio (1.06 to 1.11) mixes
the two and should not be read as the effect of tuning. By Palace's own timers,
the error estimator takes 35.2 s of a 102.1 s run at 1 rank (`Save = 0`, tuned)
and 4.7 s of a 22.3 s run at 8 ranks, and ParaView output takes 73.3 s at 1 rank
with `Save = 6`. The tuned build's largest rank peaks at 2.47 GB at 1 rank, against
2.20 to 2.24 GB untuned.

The port-aware row is the issue #514 route as it stood at geode `8367ee7b` (and
`61e8571e` for PR #964), before PR #1002. PR #1002 (#950) renamed that route
`GEODE_GAUGE=port_aware_extract` and gave the name `port_aware` to a
single-factorization port-subspace projection. That route returns the six
physical modes for a 7-mode request, alongside one non-physical mode: the
3.45 GHz port mode (#1003). It has not been timed on m6i; its local single-thread
numbers are `[issue_950]` in
[`results_like_for_like_local.toml`](results_like_for_like_local.toml). The
times in this table are not re-run.

The historical request (6 @ 4.5 GHz) returns 1 of the 6 modes. It was re-run for
continuity at 30.9 s and 25.2 s (1 and 8 threads) and is in the TOML, not in
this table. The TOML also gives every ratio against the same-box untuned build.

**What this shows, on this mesh and this instance type only.** Tuning Palace
moves every ratio above by 1% to 5%. Without field output (`Save = 0`) at 8
wide, tuned Palace has the lower wall clock than every geode request:
22.3 s against 25.2 to 47.1 s. With the fixture's `Save = 6` at 8 wide, the two
oracle-tuned geode requests take less wall clock (25.2 s and 26.7 s against
31.6 s) and port-aware takes more (47.1 s). At 1 wide, every geode cell takes
less wall clock than tuned Palace in both configs. In every cell geode uses
fewer core-seconds, by 1.62× to 6.89×.

**Caveats.**

- MPICH ranks busy-wait, so Palace's core-seconds are close to ranks × wall by
  construction (cpu_percent 799 at 8 ranks). The core-second ratios overstate
  the CPU work Palace needs.
- The two oracle-tuned geode requests need the Palace answer to set them up.
  The port-aware request timed here (the #514 route) returned two non-physical
  modes. The current `port_aware` route (PR #1002) returns one, the 3.45 GHz
  port mode, which is tracked in #1003.
- `Save = 0` removes Palace's field output, not its error estimator. geode has
  no counterpart for the estimator.
- One mesh (133k DOFs). Nothing here says anything about other sizes; the
  committed record has the direct path losing on both axes at 1.16M DOFs.

No winner is declared.

**Not done.** These were not tried:

- MKL;
- each tuning change on its own (only the combination was built);
- other Palace linear solvers, and Palace without its error estimator;
- geode built for the host CPU;
- the alternative-request cells of PR #964;
- other meshes.
